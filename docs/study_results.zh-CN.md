# 怎样阅读和发布实验结果

[English](study_results.md) | **简体中文**

test 主实验和 train 补充复核分别报告。每份报告先说明执行覆盖：计划槽位、已有首次尝试、有效结果、已评分但未满分、无效尝试和未启动槽位。重复 trial 不能算作更多独立任务。

## 离线生成报告

[`report_study_evidence.py`](../benchmark/tau3/scripts/report_study_evidence.py) 读取一个精简证据包，先核对来源版本和聚合，再在新目录中写入 `summary.json`、`report.md` 和 `report.zh-CN.md`。它不调用模型，不需要凭据或原生 benchmark checkout。两种语言使用同一份统计结果，不覆盖已有文件。

```bash
.venv/bin/python benchmark/tau3/scripts/report_study_evidence.py \
  --input artifacts/frozen_study/retail-holdout-v1c/public_evidence.json \
  --output artifacts/frozen_study/retail-holdout-v1c/cohort_report
```

[精简导出与审计](../benchmark/tau3/studies/retail-holdout-v1/README.zh-CN.md#精简证据复算) 在打包前核验本地原始证据。公开 clone 可用匹配版本的精简包和源码重新生成报告。这能复算已报告指标，不能独立重新评分未公开的完整轨迹。

## 核对案例记录

[`audit_study_cases.py`](../benchmark/tau3/scripts/audit_study_cases.py) 将脱敏 `case_index.json` 与匹配的精简证据核对。两份文件就绪后，使用它们的实际路径：

```bash
.venv/bin/python benchmark/tau3/scripts/audit_study_cases.py \
  --evidence /path/to/public_evidence.json --cases /path/to/case_index.json
```

入口先审计证据包，再检查每个案例对应的原始 attempt、outcome 哈希、simulation 哈希和冻结指标。它从脱敏工具事件序列复算调用总数、明确错误、未知结果、同消息重复和跨轮重复。案例身份重复、工具事件遗漏、指标不符，以及额外的原始参数或消息字段都会被拒绝。没有工具调用的案例也可以核验。

记录只保留参数哈希和消息位置。位置与角色只能检查内部一致性，公开入口不能证明它们与未公开轨迹相符；来源哈希也只是标识本地证据，不能认证其真实性。语义解释仍依赖作者对原始轨迹的核验，选取的案例不是随机样本或独立标注。这个入口先于最终案例发布，不证明实验已结束。

## 分母和缺失结果

| 字段 | 含义 |
|---|---|
| 有效首次尝试 | 保留了官方 reward 的首次尝试，包括部分分数 |
| 首次成功 | 有效首次尝试中官方 reward 恰好为 1 的结果 |
| 已评分但未满分 | 有效首次尝试中 reward 低于 1 的结果，与基础设施失败分开 |
| 无效首次尝试 | 已保留但没有有效评分的尝试；原始状态不改写 |
| 未启动槽位 | 计划中还没有首次尝试的槽位，不存在模型结果 |
| 补跑 | 无效首次结果之后的单独尝试，不替换首次记录 |

报告同时列出成功/有效首次、成功/全部已尝试首次和成功/全部计划槽位。后两项还反映执行覆盖，不能直接解释为模型成功率。分母为零时显示 `NA`。补跑后的有效槽位数是次级覆盖，不改变首次区间或工程门槛。

报告列出**所有计划配对**中没有两条有效首次记录的项，包括两种条件都未启动的 trial。这补充了冻结 bootstrap 只从已有记录生成的缺失配对列表。bootstrap 本身不改：任务必须有完整三次有效 U0/U2 配对才能进入主区间。任务级、共享实体和近重复敏感性分别保留。业务家族表也显示计划和有效分母。

事件诊断分别统计全部已保留首次尝试和有效子集。候选计数不证明任务失败的原因，[冻结字段的覆盖限制](budgeted_execution.zh-CN.md#验证与结果边界) 仍然适用。token 和原价估算覆盖本证据包的全部阶段，包括 smoke 和补跑，不包含其他历史批次或账户消费。reasoning 已包含在输出 token 内，不重复计费。缺失用量继续保留预留。

## 发布完整实验或停止结果

未完成报告始终是快照，即使运行器后来停止。生成器不能推断停止原因，也不代表可以发布。发布完整实验或不完整诊断前，需要：

1. 确认相关运行器和 worker 已停止，全局、监督器和批次锁均释放。核对每个已保留 outcome，付费尝试不能尚未落盘或遗漏于账本。
2. 核验冻结来源及每份 outcome、轨迹、请求的哈希。保留首次和全部补跑。全历史费用审计留在本地，估算和账单核验情况分别说明。
3. 从稳定的原始证据导出。默认入口要求全部首次槽位已有记录；预算或工程停止时，`--allow-incomplete` 只生成明确标注的不完整诊断，不认证停止状态。
4. 写明保存的停止原因、实际覆盖、剩余槽位、工程门槛是否通过及复核是否运行。test 与 train 证据分开。组件归因前，按消息位置和来源哈希核验代表案例。
5. 在独立公开源码副本中分别审计、生成两个批次的报告。只发布核验过的精简指标、来源、案例和双语报告；raw 日志、凭据、账户余额及个人准备资料不进 Git。

跑完计划意味着首次尝试已保留，不意味着每条都有效，也不意味着 Agent 有提升。停止的实验仍可给出可审计的诊断边界，报告应直接说明这个边界，不能填补未启动槽位或用补跑修饰首次分母。
